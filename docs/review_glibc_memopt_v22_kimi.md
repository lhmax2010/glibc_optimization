### 2.1 Detailed concern: L2 “p99 ×20+” is profile-specific

The v2.2 text collapses the four Batch 2 profiles into a single dramatic figure. Recomputed p99 ratios vs `C0`:

| profile | T-L2 p99 ratio | C0 p99 (ns) | T-L2 p99 (ns) |
|---|---|---|---|
| small-churn | ×1.41 | 453 | 640 |
| mixed | ×20.23 | 1,171 | 23,696 |
| large-transient | ×1.19 | 29,424 | 35,090 |
| thread-churn | ×13.04 | 1,481 | 19,317 |

Only `mixed` reaches ×20. `large-transient`, despite a −42% throughput drop, has p99 only ×1.19 because its baseline p99 is already dominated by large mmap/munmap latency. The doc’s “p99 ×20+ (1.2 μs → 27 μs)” is therefore an accurate summary of the `mixed` profile, not a universal L2 signature. This matters for the envelope gate: services with a `large-transient`-like size distribution may see throughput loss without the same latency tail explosion.

### 2.2 Detailed concern: L2 thread-churn Rss inversion has high variance

Per-rep T-L2 − C0 Rss deltas in `thread-churn`: **+26,444 kB, +18,900 kB, +7,360 kB** (mean +17,568 kB). The spread is large relative to the mean. The doc’s “+8~+26 MB” captures the observed range, but presenting it as a confident envelope on n=3 is a stretch; a single additional repeat could shift the bounds materially. Treat it as **directionally confirmed**, not a calibrated distribution.

### 2.3 Detailed concern: R11 “≈0 memory return” is slightly too strong

`tcache_count=0` did reduce Rss in `small-churn` (−19 kB, −1.9%) and increased it in `thread-churn` (+1,668 kB, +2.3%). These are small in absolute terms and within noise, so the practical conclusion stands. But the doc’s “≈0 to +1.6 MB everywhere” actually undersells the `thread-churn` increase; on n=3 it is indistinguishable from noise, which is the correct framing.

## 3. Part B — audit of `bench/alloc_bench/alloc_bench.c`

### 3.1 Structural biases

| Bias | Anchor | Effect |
|---|---|---|
| **Fixed 4 threads, fixed live-set sizes** | default threads = online CPUs (`:533`); profiles hard-code `live_set=256` (`small-churn`, `:451`) or `4096` (`mixed`/`large-transient`/`thread-churn`, `:467`); Batch 2 harness pins `--threads 4` | The benchmark samples a single concurrency point. It cannot detect whether `arena_max=2` is bad only at 4 threads or bad at any concurrency. Live-set size is not scaled with object size, so RSS comparisons across profiles are not normalized. |
| **Uniform random replacement in live pool** | `idx = xorshift64(&rng) % cfg->live_set` (`:354`) | Every object has roughly the same geometric lifetime. No long-lived cohort, no generational cooling. This favors allocators that rely on steady-state reuse (tcache, fastbins) and under-tests fragmentation from interleaved lifetimes — the surface `arena_max` and `mxfast` are meant to affect. |
| **Synchronous thread churn** | per-worker deadline starts at creation (`:286-287`); all workers exit when deadline hits (`:304-312`); main recreates joined slots (`:798-817`) | Produces generational waves of exit/create. This exaggerates the arena-reuse fragmentation behind the Batch 2 L2 RSS inversion. Real services usually have staggered turnover. |
| **Write-touching pattern** | `touch_alloc()` (`:163-173`): full memset for `<128 B`, only first/last 64 B for larger objects | Large objects are barely dirtied, so measured RSS for large-object profiles is lower than a real service that writes whole buffers. Masks demand-paging / zero-page effects and makes mmap-related levers look better than they are. |
| **Latency samples only every 64 ops and excludes `free()`** | `sample_latency = counted && ((ops & 63) == 0)` (`:332-335`); timestamp covers only `malloc()` (`:337-342`) | Misses rare large stalls (consolidation, unsorted-bin scan, arena contention). Cost of L11/L12 often appears at free-time or in a later malloc that drains the backlog. |
| **RSS sampled only at end of measure phase** | three `smaps_rollup` samples 100 ms apart (`:903-910`), median (`:1007-1012`) | Captures steady-state RSS but misses transient peaks. For burst-free levers (L11/L12), the peak right after a burst free is the metric of interest. `VmHWM` is read once at idle (`:927`) with no time resolution. |
| **Idle phase measured while live pools are retained** | `sleep_seconds(cfg->idle_s)` (`:917`) after `PHASE_IDLE` but before joining workers / freeing pools (`:929-931`) | The “idle” sample is *quiescent with live objects*, not memory after the workload has freed its working set. This is why L11/L12 appear to have zero effect: there is no burst-free surface to retain. |
| **Duration mode does not normalize allocation intensity** | `--duration` vs `--ops-per-thread` (`:590-599`) | In ops mode, elapsed time is dependent, so slower levers lower throughput mechanically. In duration mode, all threads run the same wall time but intensity is uncontrolled. Neither mode separates per-op latency from throughput. |

### 3.2 Recommended additions to give L11/L12 a fair test

The built-in profiles are *live-pool replacement* workloads: every `malloc` immediately pairs with a `free` of a live object (`:337-358`). That pattern generates almost no fastbin backlog and almost no unsorted-bin backlog. Two new profiles are needed.

#### 3.2.1 L11 `mxfast` — `burst-free-small`

Target the fastbin range. On armv7l `DEFAULT_MXFAST = 64 B` (`malloc/malloc.c:836-838`); fastbin chunks are not consolidated until a `free() >= FASTBIN_CONSOLIDATION_THRESHOLD` (`malloc/malloc.c:1749`).

External histogram (`burst-free-small.hist`):

```text
16  40
24  40
32  30
48  20
64  15
```

The worker must periodically **free the entire live set at once** and then pause before reuse. Minimal code addition:

```c
// struct config
int burst_free_period_ops;   // e.g. 4096
int burst_hold_ops;          // e.g. 128
```

Run matrix:

```sh
# C0
./alloc_bench.armv7l --profile external:burst-free-small.hist \
  --threads 4 --live-set 2048 --duration 30
# L11
env GLIBC_TUNABLES=glibc.malloc.mxfast=0 ./alloc_bench.armv7l \
  --profile external:burst-free-small.hist --threads 4 --live-set 2048 --duration 30
```

Key metrics: `VmHWM`, idle RSS, and `malloc_info` fastbin block count.

#### 3.2.2 L12 `tcache_unsorted_limit` — `unsorted-drain`

`tcache_unsorted_limit` caps chunks pulled from the unsorted list during tcache refill (`malloc/malloc.c:4226-4236`). Exercise it by freeing a large mixed-size batch so the unsorted bin fills, then allocating a new mixed batch that does not exactly match the freed sizes.

External histogram (`unsorted-drain.hist`):

```text
64       10
256      15
1024     20
4096     20
16384    15
32768    12
65536     8
```

Same burst-free mechanism as above, with larger live set and longer hold.

Run matrix:

```sh
# C0
./alloc_bench.armv7l --profile external:unsorted-drain.hist \
  --threads 4 --live-set 4096 --duration 30
# L12
env GLIBC_TUNABLES=glibc.malloc.tcache_unsorted_limit=3 ./alloc_bench.armv7l \
  --profile external:unsorted-drain.hist --threads 4 --live-set 4096 --duration 30
```

#### 3.2.3 Cross-cutting: add peak-RSS sampling

Add a background sampler that records `/proc/self/smaps_rollup` every 50 ms during the measure phase and reports max/median, or at minimum sample immediately after a burst-free event. Without this, L11/L12 transient wins are invisible.

## 4. Part C — new directions not in v2.2

### 4.1 L2 variant: per-core `arena_max` instead of fixed `=2`

The source cap formula is core-based: `NARENAS_FROM_NCORES(n) = n * 2` on 32-bit (`malloc/malloc.c:1921`). On a 4-core armv7l TV the default effective cap is 8 arenas. `arena_max=2` cuts it to 2; `arena_max=4` would cut it to 4.

| Setting | Expected memory vs default | Expected perf vs default | Risk |
|---|---|---|---|
| `arena_max=4` (per-core) | Halves VA/RSS fragmentation surface vs 8 arenas; less savings than `=2` | Much lower contention than `=2`; likely within budget | Needs per-service contention profile |
| `arena_max=3` | Intermediate | Intermediate | Tune by benchmark |
| `arena_max=2` | Maximum memory savings | High contention cliff on allocation-heavy profiles | Only for low-concurrency services |

**Recommendation**: add `arena_max=3` and `arena_max=4` to the Batch 2 matrix. For a 4-core TV, `arena_max=4` is likely a better default compromise than `=2`. The v2.2 doc correctly withdraws `=2` from the first-wave bundle, but it does not explore the obvious middle ground.

## 5. Top-3 challenges to v2.2 as a whole

1. **The microbenchmark is the pre-screen gate, but it structurally under-tests the levers it is supposed to vet.** All built-in profiles use live-pool uniform replacement, which gives fastbins/tcache/unsorted bins almost no backlog to act on. L11 and L12 are therefore marked UNTESTED-EFFECT for the right reason, but the tool itself should have been extended before the v2.2 consolidation rather than after.
2. **L2 is treated as a binary safe/unsafe lever rather than a continuum.** The source cap formula is per-core (`malloc/malloc.c:1921`); `arena_max=2` is an extreme cut from 8 arenas on a 4-core device. The obvious intermediate settings (`=3`, `=4`) are never mentioned, even though they could recover most of the memory savings without the contention cliff.
3. **v2.2 scopes kernel/system MM levers as “covariates” only, leaving substantial RSS/PSI wins on the table.** `vm.overcommit_memory=2` and THP mode are not just covariates — they directly change glibc’s reclaim behavior (`malloc/arena.c:516-525`, `nptl/allocatestack.c:372-376`). Treating them as out-of-scope is defensible for a glibc-only plan, but the doc’s north star is RSS/PSS/PSI, so the omission should be explicitly flagged as a boundary decision, not a technical non-issue.

## 6. `negative_facts` — checked and confirmed absent/false

- The adjudication files `docs/ab_batch1_adjudication_zh.md` and `docs/ab_batch2_adjudication_zh.md` referenced in v2.2 §0b are **not present** in this commit; conclusions were reconstructed from the batch reports and design doc alone.
- `tcache_count=0` (R11) does not reduce the per-thread `tcache_perthread_struct` allocation; that requires a `USE_TCACHE=0` rebuild (`malloc/malloc.c:3241-3268`, already noted in v2.2).
- Glibc itself already ships full RELRO + BIND_NOW + DT_RELR when supported; no linker-hardening memory win remains *inside* glibc.
- `arena_max=2` is not the only L2 setting; the source default cap is `2 × cores` on 32-bit (`malloc/malloc.c:1921`).
- `MALLOC_PERTURB_` is live in normal libc (`malloc/malloc.c:5468`, `elf/dl-tunables.list:39-43`); only `MALLOC_CHECK_` is a stub (v2.2 G2 is correct).

## 7. `cannot-verify` list

- Whether `arena_max=3/4` would pass the 5% perf budget on real TV services.
- Actual TV kernel config: MGLRU, zram/zswap, KSM, THP mode, `vm.overcommit_memory` default.
- Whether `vm.overcommit_memory=2` image-wide would break any Tizen service on the real TV image.
- Real-service allocation contention profiles for L2 envelope gate.
- L11/L12 effects under a true burst-free workload (needs new `alloc_bench` profiles).
- Peak-RSS behavior of L3/L6 under TV application phase changes (current sampling misses peaks).
- Whether cold-DSO `-Os` / section-GC pass glibc ABI and gconv/NSS tests.
