Return freed memory to the system

After the application releases objects in batches, this approach conditionally calls glibc's malloc_trim(0) to return reclaimable free pages still held in the heap to the system, reducing process memory usage.

malloc_trim is a glibc runtime interface that attempts to return whole pages that are free in the allocator but still occupy physical memory to the kernel. The operating system reclaims memory in pages: if a page contains data that must be retained, the entire page cannot be discarded. Therefore, bytes released by free do not necessarily become reclaimable pages immediately.

Process memory savings are clear. For the longest-running operations, the change with this approach remains within the variation observed across repeated runs without it. No additional slowdown was observed for those operations; this does not mean zero impact on every performance measure. Typical operation times still show a small change, disclosed below. This report does not claim improved performance or treat limited tests as proof of long-term stability.

This report organizes existing published evidence; it adds no measurements. Benefits refer to reclaimed process memory, not demonstrated whole-system or product benefits.

At a glance

This report covers two batch allocation-and-release workloads: a varied-size allocation workload repeatedly allocates objects of different sizes and releases a portion in batches; a mid-size-heavy allocation workload follows the same process, mainly with medium-sized objects. Media decoding loops repeatedly perform software decoding, stop the pipeline and release its resources before the next cycle. The resident UI compositor process, enlightenment, provides a contrasting use case: it continuously handles display composition, rather than primarily releasing large batches of objects.

The no-call comparison uses the same executable and workload parameters but does not call trim. Measurements are taken at corresponding points in runs with and without trim. RSS is the process's total resident physical memory, including code, stacks, shared pages and other mappings. Heap Private_Dirty (heap PD) counts only the private dirty pages classified as glibc heap in this report; it does not cover the same memory as RSS. Memory charts use MiB or KiB.

To avoid representing the tests with one potentially unusual run, a 'typical value' below is the middle number after ordering the repeated results; if there are two middle numbers, it is the value halfway between them. 'Run-to-run variation' means the difference between the largest and smallest results under the same conditions.

Calling trim at a release point has a cost. The longest-operation change staying within no-call variation does not mean zero impact on every measure. The small change in typical operation time, the page-fault cost when memory is reused, and unverified concurrency effects must all remain visible.

Not observing a slowdown does not mean zero impact on every metric, nor prove that product service quality is entirely unchanged. In the same data, selecting a typical operation time for each run and comparing the typical repeated results gives an increase of +1.870462 ms. This exceeds the 0.173927 ms no-call variation and is an observable small slowdown. Here, a run's typical operation time is the faster of its two middle cycles after ordering its 50 cycles from fastest to slowest. There is still no proof that lock stalls have no effect on arbitrary actively concurrent threads.

Page faults and stability: observation periods and exceptions matter

A minor fault can be handled without reading a page from backing storage; a major fault requires a page to be brought in. An increase in the former commonly reflects rebuilding page mappings and must not be confused with the latter. OOM/LMK refers to out-of-memory or low-memory process-kill records. zram is compressed swap in memory; we record changes in its original data size, compressed data size and memory use.

  • major fault: Major faults are 0 in the system before-and-after observation periods and 0 in defined next cycles; missing final-cycle values are not counted as zero. They are also zero in the allocation workloads' next cycles, and the decoding observations for cycles 2–51 likewise give 0.
  • Cold-start exception: The first cycle of the first no-trim decoding repeat had 4 major faults before any trim; the external series also records 4. They are not attributed to trim, but 'zero throughout all experiments' would be incorrect. Missing auxiliary fields in the earlier decoding experiment are not treated as zero; valid in-process and external series take precedence.
  • Cost when memory is reused: The varied-size and mid-size-heavy allocation workloads add +1351 / +1465 minor faults in the next cycle, respectively. For decoding, we compare typical per-run fault totals and divide the difference across cycles, giving about +359 per cycle. This is consistent with rebuilding mappings after free pages were discarded. A minor fault itself does not require a page read from disk; this does not promise that the process performs no other disk I/O.
  • Observed stability: There are no OOM/LMK records in the allocation and decoding observation periods, and all three zram changes are 0. The decoding target exited normally. Across completed observations of the resident UI compositor, the process ID and start identity remained unchanged, with no crash or restart observed. These limited observation periods are not proof of long-term anomaly-free operation.
  • Not every historical run was alert-free: The large-area release reference has a recorded known-alert waiver. The trigger and timing are reproducible, but harmlessness has not been established by root-cause proof. The system before-and-after experiment ran in phases with delayed cleanup completion and known nonempty directories retained. It cannot be described as uninterrupted running with no residue.

Integration effects and selective use

The with-call and no-call runs use the same executable, selected by runtime parameters. They do not replace libc, and the switch does not change binary size or build artifacts. Startup time was not measured separately. A release-point design does not require trim on the startup path, but unchanged artifacts do not prove identical startup time. Whether adding a product call site requires changes by the target's maintainer depends on the integration method.

Targets that do not meet the conditions can omit the call entirely and incur no added trim-call overhead. This reduces the affected surface; it is not a guarantee of zero system-wide risk.

Where it applies: clear batch-release savings, small savings in measured resident services

The resident UI compositor reclaimed 272 KiB / 36 KiB in its initial observation and after application release, respectively. Three later observations reclaimed 88 / 0 / 4 KiB. The later typical RSS reduction is 0.003906 MiB / 0.033659%, below the 0.089844 MiB variation across repeats, so a real change is not established. Typical injection time is 1899.209517 ms. This includes attaching gdb and using ptrace to control the process. It must not be combined with the approximately 1 ms release-point call costs.

Resident free-block bytes are not the same as reclaimable bytes. Whole free pages and allocator state constrain reclamation; fragmentation can prevent many free bytes from forming reclaimable pages. These aggregate observations cannot uniquely identify block addresses or the mechanism used. The whole-page estimator's predicted interval failed to include the measured value in all 15/15 strictly paired observations. Predictions based on free-block sizes therefore cannot replace an actual trial call.

Product use: all four conditions must hold

Exclude memory already returned automatically → confirm freed memory remains in the heap → measure sufficient trim savings → confirm costs are within budget

  1. Do not add reclamation for the part of a cycle that already returns memory automatically. A spontaneous fall in heap PD is not evidence that trim is needed.
  2. Use glibc's malloc_info interface to inspect free blocks in each allocation area and confirm that freed memory remains resident. A flat memory curve in the kernel's smaps output does not establish that all of that memory is reclaimable.
  3. Try trim on the same target at the same release point and measure the actual savings. They must meet a threshold fixed in advance; predictions from free-block sizes are not a substitute.
  4. Call time, next-cycle faults and lock stalls under active concurrency must all meet the business budget. Do not enable the call unless these conditions hold.

Limits and open work

  • Test-board scale, not a product-benefit claim. Process RSS reclamation is clear, but available system memory did not change beyond the measurement's own variation. This does not establish whole-system or business benefits.
  • Persistent memory usage in product candidates has not yet been reconfirmed or separated into live objects and freed blocks. Target maintainers must help collect heap information. Memory that stops decreasing in a trace can only identify candidates for further investigation.
  • Real-concurrency cost coverage remains incomplete. Synthetic workloads do not cover product concurrency. The decoding experiment calls trim after the pipeline stops and releases resources, covering only that release point and later-cycle costs. It does not directly quantify allocation-area lock contention during active allocation, frame latency or energy use.
  • Image, memory-environment and workload differences matter. The test board's object sizes, allocation history and release patterns are not substitutes for the product environment. Product use requires validating the enabling conditions again.
  • No blanket enablement promise. Measured resident-service savings are small. Neither resident free-block bytes nor the whole-page estimator provides a universal savings threshold. No observed additional slowdown of slower operations does not mean every performance dimension is unchanged.
