在 C 运行时层(glibc / ptmalloc)降低 Tizen 平台的运行时内存占用与系统内存压力,而非逐个应用改造。

- 北星指标：进程级 RSS/PSS + 系统级 PSI(内存停顿)

## 2. 方案调研全景

### 2.1 调研方法

对 Tizen glibc 2.40 源码树做逐项审计,覆盖 `elf/dl-tunables.list` 与 `sysdeps/nptl/dl-tunables.list` 的**全部**内存相关旋钮,加上分配器内部机制(arena/tcache/fastbin/trim/mmap 阈值)、动态加载器、locale/gconv、NSS、打包策略。每个候选给出:机制证据(file:line)、预期收益量级、性能代价预判、上线方式、风险。

覆盖闭合性已由独立评审核验:所有内存相关 tunable 均已归入"存活杠杆"或"已否决"两类,无遗漏项。

### 2.2 存活杠杆(经实证保留)

| ID | 杠杆 | 类型 | 上线方式 | 实证状态 |
|---|---|---|---|---|
| **L6** | 相位切换点主动 `malloc_trim(0)` | RSS | 代码(一行调用) | **收益已定量可预测**:回收率 ≈ 释放比例 × 0.98(中大尺寸),归还率 110~143%(按整页归还,收益大于释放字节数);小对象(<256 B)仅 27.9%,碎片化释放打七折(§3.8)。作用条件为"进程自身 glibc 堆批量 free 后仍有未归还页"；**PD 可见下降是反信号**，表示该周期分量已自动离开私有脏页；PD 不降也只是一项必要表型，仍须 `malloc_info` M7 确认 bins 驻留。常驻 UI 组件与自带分配器的运行时(Chromium/.NET/GStreamer 硬解)均已排除 |
| **L3** | 钉死 `mmap_threshold` / `trim_threshold` | RSS | env 或 `mallopt()` | 代价 ≈0%(四档负载);连续大块 churn 档 −4.9%;收益 −0.9~1.6 MB |
| **L1** | 缩小 `pthread.stack_cache_size`(40MB→1MB) | RSS | env | churn 档 −1.0 MB、代价 0.0% |
| **L2** | `arena_max` 上限 | RSS | env 或 `mallopt()` | 超订比门控:线程:arena=1:1 时免费(+1.0%/−1.6MB);4:3 −22%;4:2 −46%;线程 churn 场景任意 cap 均反向增长 +11~21MB → 该类禁用 |
| **L7-L10, L18-L19** | gconv 裁剪 / NSS 拆分 / 调试符号策略 / 镜像包审计 / 冷 DSO -Os / CLI 子包化 | FLASH | spec 与镜像构成 | 机制确认,MiB 级;待产品编码清单与镜像构成输入 |

**首发包**:L1 + L3(组合已验证,+0.1% / −2.43 MB,无相互作用惩罚)。

### 2.3 已否决清单(14 项,按证据强度分级)

否决项按证据性质分三级。**分级的意义在于明确哪些是定论、哪些是当前结论**:机制级不可推翻;实验级受负载覆盖限制,满足重开条件时应重新评估;成本级为条件性搁置。

#### A 级 · 机制性否决(源码层面证明不存在收益,不可推翻)

| ID | 项 | 否决依据 |
|---|---|---|
| R1 | `top_pad=0` | 分配器实际默认已是 0(tunable 元数据 131072 为死值);显式设置反而副作用禁用动态阈值 |
| R2 | `arena_test` | 非上限旋钮;设置 `arena_max` 后不参与判断 |
| R3 | `rseq=0` | 32 字节 rseq 区内嵌于 `struct pthread`,关闭不改变结构体尺寸 |
| R4 | `mmap_max` 调低 | 减少可独立 munmap 的大块,方向上即为 RSS 负收益 |
| R5 | `__libc_freeres` | 一次性退出路径 API,有 `already_called` 守卫,不可重复调用 |
| R7 | locale-archive 最小化 | Tizen spec 已是最小 locale 配置,无可裁减项 |
| R8 | static TLS surplus 类 | surplus 区 demand-zero,线程创建时不触碰 → RSS 恒为 0 |
| R9 | dlconf 禁用(为 RSS) | 稳态 RSS 实测 ≈0(配置/缓存映射为瞬态) |
| R10 | 线程 guard page 移除 | guard 页为 `PROT_NONE`,不占 RSS |
| R14 | `hugetlb` | 32 位下 `heap_max_size()` 膨胀至 8 MiB/arena,为反向杠杆 |

#### B 级 · 实验性否决(基于合成负载实测,受负载覆盖限制,可重开)

| ID | 项 | 当前证据 | 重开条件 |
|---|---|---|---|
| R11 | `tcache_count=0` | 四档合成负载吞吐 −5.7~−10.1%,内存回报 ≈0(chunk 迁入 bins) | 若实测发现某类真实进程 **tcache 驻留量达 MB 级**,应重新评估该类目标 |
| R12 | `mxfast=0` | 定制 fastbin 积压负载上 −5.6% 换 −31 kB;该数字在 `burst_size=2048` 下测得 | 若实测发现真实进程 **fastbin 积压显著大于该量级**(大规模突发场景),应重测 |
| R13 | `tcache_unsorted_limit` | 按其代码路径定制的负载上无可测效果 | 若实测发现真实进程存在**显著 unsorted 链驻留**,应重测 |

> **说明**:B 级三项与 L6 的情况同型——结论建立在自建合成负载之上,负载未覆盖的场景构成盲区。§3.5 的广度扫描将通过在真实进程上采集 `malloc_info()`(tcache 驻留、fastbin 积压、unsorted 链长)一次性取得这三项的真实分布,据此判定是否重开。

#### C 级 · 成本性搁置(收益可能存在,代价面无法评估)

| ID | 项 | 状态 |
|---|---|---|
| R6 | libc 整体 `-Os` | 非"无收益",而是性能风险无法从源码界定;另有实证:Tizen 树在 -Os 下 `libnss_optfiles` 链接失败(隐藏符号 `__feof_unlocked`)。需专门实验构建与完整 benchmark 套件方可评估,当前条件不具备 |

### 2.4 范围外项(既非杠杆也非否决)

以下旋钮有内存或运行时语义,但不属于"优化候选"二分法,单列避免误用:

| 项 | 定位 |
|---|---|
| `glibc.mem.decorate_maps` | **观测工具**——不降低 RSS,但可精确标注 arena 区间,是归因度量的关键能力(需内核 ≥5.17) |
| `glibc.mem.tagging` | **平台安全能力**(aarch64 MTE)——不得为省内存而关闭 |
| `glibc.malloc.check` / `perturb` | **诊断开关**——误开会造成严重性能与内存退化,属环境卫生审计项 |
| `glibc.pthread.mutex_spin_count` 等 | 内存中性,仅影响同步性能 |

### 2.5 版本依赖

本报告全部结论基于 **glibc 2.40**(产品板与测试板一致)。已核实上游 2.41 的 malloc tunable 集与 2.40 完全相同、无新增内存旋钮;但有两个提交会改变现有结论的机制基础,**若平台升级至 2.41 需重测**:

- `e2436d6f5a`:释放的小 chunk 直接进 smallbin 而非 unsorted → R13 的否决依据需重验;
- `226e3b0a41`:calloc 增加 tcache 路径 → R11/L4 的成本收益曲线会变。

### 3.4 真实进程回收天花板(2026-08-06 实测)

为验证合成数字能否外推,在 RPI4 上对真实应用(重启→负载→静置)实测两条路线,并在产品板做只读画像。

**实测结果(每轮重启目标保证新鲜态,n=3 取中位数)**

| 目标 | 总私有脏页 | **L6 实测回收(`A_ceiling`)** | 占总私有脏页 | 页级路线可迁出(glibc 区间 / 其余匿名) |
|---|---:|---:|---:|---:|
| AppUIA(.NET 系) | 13.4 MiB | **0.219 MiB** | 1.47% | 2.78 / 4.84 MiB |
| AppUIB(原生 EFL) | 30.7 MiB | **0.438 MiB** | 1.40% | 7.86 / 16.44 MiB |

测量可信度:六轮 `malloc_trim(0)` 均返回 1(确有释放)、zram 计数器零变化(为真释放而非迁移)、`A_ceiling < B_glibc` 符合理论(trim 只能还空闲页,pageout 迁走全部页)、无挂死/超时/异常。

**结论(限定于已测目标)**

- 已测的两类目标(.NET 常驻 UI、原生 EFL 常驻 UI)上,L6 回收量为亚 MB 级,可回收部分约占其 glibc 堆的 4.5~5.0%;
- 与合成基准 59.9 MB 的差异有明确机制解释:合成负载**刻意释放了 50% 的对象池**以制造空闲页;这两类常驻组件处于稳态运行,堆中以存活对象为主;
- **样本限制(重要)**:n=2,且两者同属"稳态常驻 UI 组件"这一类。该结果**不能外推为全平台规律**——分配模式差异大的目标(AIFW 的模型加载/推理释放、Web App 的 WRT 实例、各类 Native App)尚未取样,其中可能存在收益显著更高的作用点。搜索计划见 §3.5。

**产品板只读画像(Top-5 目标)**

| 分类 | 合计私有脏页 | 占比 | 本路线可否触及 |
|---|---:|---:|---|
| glibc 堆 | 40.6 MiB | 37% | 可触及,但按实测比例(约 5%)现实预期仅 ~2 MiB |
| 其余匿名(GC 堆 / JIT 等) | 44.5 MiB | 40% | **任何 libc 层方案(含替换分配器)均不可触及** |

**方法限定**:页级数字经 `process_madvise(MADV_PAGEOUT)` 测得,页被迁往 zram 而非释放(实测压缩比 3~5:1),系统净省小于迁出量;`malloc_trim` 走 `MADV_DONTNEED` 直接释放,无此折扣。

### 3.5 L6 作用点搜索(进行中)

L6 的收益直接取决于目标在触发时刻堆内**已释放但未归还**的页量,该值随应用类型与分配模式差异显著。因此本项工作的重点从"验证单一目标"转为**系统性搜索最佳作用点**。

**已完成的能力建设**:
- lldb 注入法已跑通,单进程 `A_ceiling` 测量成本降至分钟级(6 轮一次会话完成);
- **`malloc_info()` 经 lldb 注入变为进程外可达**——此前该 API 被认为只能进程内调用,是度量协议的长期空白;现可对任意进程取得 arena/tcache/fastbin/unsorted 的细粒度归因;
- `reclaim_probe` 可对任意进程做 glibc 堆 / 其余匿名 / 文件映射的私有脏页分类;
- 新鲜态纪律(每轮重启目标)与归因校验(zram 零变化)已确立。

**已确认的关键结论**(2026-09-01 修订,详见 §3.6 与 §5.3):作用面的决定变量不是目标标签，而是**批量 free 后仍有未自动归还的 glibc 页**。搜索重点调整为“识别释放相位 → 用 M7 确认 bins 空闲字节增长 → 确认 PD 尚未自动下降 → 再触发”，而非只凭操作结束或 PD 峰谷选择时刻。

**反信号原则（2026-09-01 新增）**：若 glibc-heap PD 在释放后出现可见下降，且 zram 无正增长、majflt 为零、total PD 同步下降，则该下降分量已经由自动归还路径离开私有脏页集合，不能再计入 L6 候选收益。反之，PD 不降不等于“已证明可 trim”；它只保留候选资格，仍须 `malloc_info` 的 unsorted/rest 增长确认 live/bin 属性。

**搜索计划**:
1. **广度扫描**:对测试板上全部可测进程逐个测量 `A_ceiling`,取得收益分布而非单点,识别离群目标类别;**同批采集 `malloc_info()`**,一并取得 B 级否决项(R11/R12/R13)在真实进程上的驻留分布,据此判定是否重开;
2. **类别覆盖**:重点补充 AIFW(模型加载→推理→释放,天然具备分配高峰相位)、Web App(WRT 实例)、Native App(自定义分配模式)、以及具备明确"批量释放"语义的组件;
3. **相位驱动**:对高潜力目标构造"大量分配→集中释放→触发"的驱动方式;输入自动化受限时使用 `/dev/uinput` 或应用自带的可脚本化接口;
4. **代价面同测**:trim 期间的全 arena 锁停顿(此前实验均在线程静止态)与 trim 后 refault,与收益同批测量,确保每个作用点的净收益为正;
5. **产品板映射**:测试板取得的"收益/glibc 堆"比例分布,结合产品板的只读画像,给出产品侧收益的上下界估计。

**探查已排除的目标**(六候选,`docs/l6_target_feasibility.md`):平台 player 与 GStreamer 路径的解码缓冲不落在 glibc 堆(播放中 90% 私有脏页位于其余匿名区间);Chromium 具备可观 glibc 堆(主进程 18.4 MiB)但当前缺少页面加载的自动化驱动手段——**该目标不排除,待输入自动化解决后重新纳入**。

### 3.6 关键发现:L6 的收益由触发相位决定(2026-08-11)

此前所有 L6 测量结果偏低,根因经实证确认**不是目标类型问题,而是触发时刻错误**。

**决定性实验**:同一进程(GStreamer 软解 320×240)、同一镜像、同一 glibc,仅改变 trim 触发时刻:

| 触发相位 | `A_ceiling` | 占 glibc 堆比例 | 相位签名(`malloc_info` unsorted) |
|---|---:|---:|---:|
| 解码中暂停(SIGSTOP) | 0.008 MiB | 0.28% | 1.6~22.6 kB |
| **解码完成、缓冲释放后(PLAYING→NULL)** | **1.359 MiB** | **48.9%** | **1.77~2.10 MB** |

- 三轮完全一致(1,425,408 B),`malloc_trim` 均返回 1;
- **规模验证(8 路并发)**:8/8 全部成功,单路回收 1.348~1.371 MiB、比例 48.5~49.4%(极差 <1 个百分点),**合计回收 10.9 MiB**;
- **回收量相差 174 倍,回收比例相差 173 倍**;
- 相位有效性的正确判据是 `malloc_info` 的**空闲字节增长**(unsorted 链暴涨 100 倍),而非 `Private_Dirty` 下降——`free()` 将内存归还 ptmalloc 的 bin,页仍留在堆内且仍为脏页,故 RSS 在释放后**不降反升是预期行为**。此前使用 RSS 下降作为相位判据是度量协议的定义错误,已修正(§6 M7)。

**对此前结论的影响**:AppUIA(4.48%)、AppUIB(5.03%)、Chromium(0.196%)、GStreamer 暂停态(0.28%)——**全部为静置或非释放相位测量**,不代表各目标在释放相位下的收益。这些目标的释放相位收益需重测。

**代价面数据(8 路并发实测)**:trim 期间目标进程 utime/stime 增量为 **0**(8 路中 1 路为 1 tick),说明全 arena 锁停顿在该规模下不构成问题;trim 后再次进入工作状态 refault 为 **519~525 minor / 0 major**,zram 全程零变化——无磁盘 IO、无换入。**代价面基本干净。**

### 3.7 作用条件的精确化:常驻 UI 组件经实测排除(2026-08-13)

图形环境修复后(装 coregl+mesa,glibc 未变动,单路 L6 回归 48.74% 确认环境未污染),对三个真实 UI 目标做释放相位测量,**三者均未通过 M7 相位判据,故按规程未注入、不取数**:

| 目标 | 构造的释放动作 | M7 结果 | 事实 |
|---|---|---|---|
| AppUIB | 启动 5 个应用后逐个关闭 | 3/3 未确认 | 空闲字节**反而下降** 27~34 kB;应用来去发生在别的进程,AppUIB 自身持有的是长期 UI 缓存 |
| AppUIA | 5 次 syspopup 调用 | 3/3 未确认 | glibc 堆 PD 逐字节不变,unsorted 仅动数百字节;UI 事件由独立进程处理,自身不做批量分配 |
| Chromium | 加载重页面后导航 about:blank | **已排除(2026-08-13 补测)** | 通过正式应用域驱动后页面真实加载并完成导航(`DidFinishLoad`+progress=1 双证据):renderer `other-anon` 下降 **25 MB**,而 glibc 堆几乎不动(主进程 0 KiB、renderer +96 KiB)——**渲染内存走自有分配器,不经 glibc** |

**由此得到 L6 的准确作用条件**——不是"应用有释放动作",而是**"进程自身的 glibc 堆经历大量分配后集中 free"**:

| 进程形态 | 是否满足 | 实测 |
|---|---|---|
| 批量数据处理(媒体解码等) | ✅ | 49%,1.36 MiB/进程 |
| 常驻 UI 组件(持有长期缓存、转发事件) | ❌ | 释放动作不触及自身堆 |

常驻组件此前测得的 4.5~5.0% 是**长期运行积累的零散碎片**,不是相位收益,两者性质不同。

> **2026-09-01 精化：** “集中 free”仍不足以单独构成 L6 作用面；若 free 后 PD 已可见下降，该分量属于自动归还反信号。正式作用条件是“集中 free 后 M7 确认 bins 驻留，且页面尚未自动离开 PD”。

**对产品侧估算的影响**:产品板 Top-5 中 `DN_*` 系为 .NET UI 组件,结构上接近本节排除的常驻组件;`ServiceE` 为 Web Runtime,与已排除的 Chromium 同源(Web 内容内存走自有分配器)。因此**不能按受控目标的 49% 外推**,详见 §5.3 的区间估算。

### 3.8 L6 作用条件定量曲线(受控扫描,36/36,2026-08-13)

为使收益可预测而不依赖"能否驱动某个应用",用受控负载扫描分配模式对回收率的影响。12 格 × n=3,全部退出码 0、零 LMK/OOM、12/12 格 M7 确认。

**曲线一:释放比例(最强自变量,近乎线性)**

| 释放比例 | 回收率 | 归还率 | trim 耗时 |
|---:|---:|---:|---:|
| 25% | 29.8% | 133.7% | 8.1 ms |
| 50% | 53.6% | 116.0% | 13.4 ms |
| 75% | 75.7% | 111.3% | 18.3 ms |
| 90% | 88.5% | 110.8% | 20.7 ms |

→ **回收率 ≈ 释放比例 × 0.98**(中大尺寸分配)。可直接用于产品侧预测。

**曲线二:尺寸分布(小对象是禁区)**

| 尺寸 | 回收率 | 归还率 |
|---|---:|---:|
| small 16–256 B | **27.9%** | 60.9% |
| mixed 16 B–64 KiB | 53.6% | 116.0% |
| medium 1–16 KiB | 50.6% | 109.0% |

→ 小对象因页内碎片凑不出整页,回收率腰斩。

**曲线三:live-set 规模** 1024/4096/16384 对象的回收率为 52.3%/53.6%/40.9%——**规模越大回收率略降**(碎片累积),但绝对回收量随规模线性增长(16.5/60.1/154.4 MiB)。

**曲线四:释放顺序(碎片化代价)** 同为 50% 释放,顺序释放 53.6%、隔一个释放 **40.6%**——**碎片化让收益打七折**,且 trim 耗时反增(19.9 vs 13.4 ms)。

**两个衍生认识**:
1. **归还率 >100%**:trim 归还的是整页,而 payload 只计对象字节;页内元数据、对齐填充与邻接空闲块被一并归还,故实际收益**大于**"释放了多少字节"的朴素估计;
2. **代价面线性可预期**:12 格 majflt 全为 0;trim 耗时随释放规模从 0.8 ms 到 80 ms(最大格释放 365 MB),可按规模预估。

**与真实目标的互相印证**:媒体解码实测 48.5~49.4%,曲线中最接近的单因素点为 medium-only/50%/high 的 50.6%(差 1.2 个百分点)——受控曲线与真实实测吻合。

### 3.9 新 LLVM 镜像 S4 锚点与滞留 trim（2026-09-01）

历史瞬时释放格在换板换镜像后失去同板可比性；新镜像各一次的 mixed/medium-only 锚点为 `51.074077% / 50.387886%`，距 `49%` 机制预期 `+2.074077 / +1.387886 pp`。旧 `53.55% / 50.60%` 只保留为不可比参考。

S2 合成滞留表型的 8 格 trim/control 测量显示：16/16 周期没有 free 后 PD 自动下降，trim 前 M7 为 MB 级 rest/unsorted；valley trim 回收 `80.175875%–85.453954%` 的 released payload，调用中位 mixed/medium-only 为 `1.233269 / 1.218361 ms`。下一周期相对 none 增加 `1351 / 1465` 次 minflt，majflt 全为 0，zram 不变。由此“反信号排除 → M7 确认 → 以已知调用/faults 代价回收”在合成代理上成立；产品候选的 live/bin、并发锁停顿、业务延迟与能耗仍未测。见 [`s4_reference_and_retention_trim_20260901.md`](s4_reference_and_retention_trim_20260901.md)。

## 4. 平台约束(实测发现)

这是本项目最重要的负面发现,直接决定实施路径:

| 约束 | 事实 | 影响 |
|---|---|---|
| **AT_SECURE** | 产品板 glibc 堆占用最高的 5 个进程全部 `AT_SECURE=1`;glibc 在此状态下直接忽略 `GLIBC_TUNABLES`(源码 `elf/dl-tunables.c:299-301`,已设备实证) | **env 路线对主收益面无效**;须改用代码内 `mallopt()` 或 L6 |
| **注入点缺失** | 上述进程为 launchpad 子进程,无 per-app systemd unit;launchpad 进程本身也不受 systemd 管理 | 无干净的配置注入点 |
| **执行策略** | 产品镜像启用签名强制,不能安装包、不能运行自建二进制 | 自建仪器无法上产品板;验证必须在测试板完成 |
| **环境差异** | 测试板与产品板在平台构建口味、CPU 调优、内存规模与回收环境上均不同 | 机制可移交,数字不可跨板外推 |

**结论**:glibc 层的优化机制是有效的,但在产品板上要拿到主收益面,必须走**代码级注入**(`mallopt()` + `malloc_trim()`)而非配置级注入。这两者都是极小的代码改动(各一行),但需要产品发布通道。

## 5. 价值判断

### 5.1 已确立的价值

1. **一个已定位作用面的高比例回收杠杆**:L6 在 M7 确认的 bins 驻留释放相位下实测回收目标 glibc 堆的 **48.9%**(1.36 MiB/进程,三轮一致),代价面为纯 minor fault、无换入(§3.6)。关键认识是**收益由释放后的驻留表型决定而非目标类型**：产品侧只有在进程自身批量 free、`malloc_info` 确认空闲字节增长且 PD 尚未自动下降时触发；单凭播放结束、内容关闭、场景切换或退后台事件不足以立项。
2. **对任意目标量化该收益的方法与工具**:lldb 注入 + `reclaim_probe` 分类 + `malloc_info` 相位判据,单目标测量成本为分钟级,使"逐目标评估、按收益启用"成为可操作的产品策略。
2. **一套可复用的证据体系**:六档负载微基准 + 度量协议 + 噪声带标定 + 配对统计判据,任何后续分配器相关工作(包括其他技术路线)都可直接复用。
3. **一份闭合的旋钮地图**:14 项否决全部带实测或源码证据,避免团队在无收益方向上重复投入。
4. **关键平台约束的提前暴露**:AT_SECURE 与注入点问题若在产品实施阶段才发现,返工成本极高。

#### 周期型目标 `ServiceA` 的定向测量(1 s 采样 × 8 轮,2026-08-14)

| 指标 | 实测 |
|---|---|

2. **glibc 周期分量确实存在但已经自动归还**：glibc P-V `6.2 MB` 实跌，且无 zram 正增长、无 majflt、无 other-anon 镜像迁移。它证明周转经过 glibc 分类，却同时是 L6 反信号，不能再当成待 trim 收益。
3. **释放在峰后至多约 9 s 的首次观测内基本完成**：逐轮旧 `fall_start` 点已释放比例为 `32.686084%–99.679693%`，形态异质；不再称“一步塌回”，也不从旧 `19.683240 s` 推导延迟钩子。

> **2026-09-01 C3 复核修正：** 原普查分类器按 a 优先，使同时越过两门的
> `enlightenment` 整体落入排除。独立复算确认其 `120 / 1736 kB = 6.912442%`，
> 未达到分类器固定的 10% 同量级门；现改为 a+b 双标签，不撤销 a 反信号，
> 但把 `+1736 kB` floor 补入候选，并保留“已证实自动归还能力”告警。

**产品侧候选面更新**：不再把 `ServiceA` 的 6.2 MB 周期分量与平台高度相加。候选转为 `ServiceH[ServiceK]` 的 2.36 MB 平台上界、`enlightenment` 的 `+1736 kB` a+b retained floor、release-ratio 中的其他 retained floor、`ServiceA` 的 `+788 kB` 谷底残渣，以及已由 `malloc_info` 确认的批量处理释放相位类；这些仍须 M7 区分 live/bin 后才能估 trim 收益。

**必须保留的限制**：只读 smaps **无法判定谷底残渣或平台高度中的 ptmalloc bin 驻留量**，也不能唯一分解 `systrim`、`heap_trim`、arena discard 与 `munmap`。产品板不能注入，候选面必须在可注入环境以 `malloc_info` M7 验证。

> **带日期撤销说明（保留历史，不作当前结论）：**
>
> - 2026-08-14 / v2.5 原表述“下降沿 19.7 s 是工程信号，产品侧 trim 钩子应在操作结束后延迟约 20 s 触发”于 2026-09-01 撤销；旧下降沿是尾窗最小值落点伪影。

### 5.2 尚未确立的

## 6. 实施计划(三周 Demo)

**目标**:在测试板上对真实进程做出可演示、可量化的收益,作为产品落地的决策依据。

**关键手段**:`LD_PRELOAD` 注入 shim —— 测试板可运行未签名二进制,故可在不修改任何产品代码、不需要跨团队配合的前提下,验证代码级注入(`mallopt` + `malloc_trim`)的真实效果。

> **前置已完成**:回收天花板与 `A_ceiling` 测量方法均已跑通(§3.4),单目标测量成本为分钟级。以下计划据此调整为**先广度搜索作用点,再定向工程化**。

### 第 1 周:驻留表型与 M7 作用面确认（S2/S4 合成代理已完成，S3 需新合同）
> 产品 `ServiceA` 的周期峰谷已归因为自动归还反信号；产品板仍受只读边界约束，无法判定平台/残渣的 live/bin 属性。
